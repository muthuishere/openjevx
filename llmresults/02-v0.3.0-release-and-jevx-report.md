# Report 2 — v0.3.0 release, 8-bit comparison, jevx CLI with real context

## Release

Shipped v0.3.0: 4-bit weight-only model (`.local/openjevx.w4.onnx`, `MatMulNBits`, block 32,
symmetric) replaces the dynamic int8 from v0.2.0. All 5 packages rebuilt and re-tested from a
clean install (macOS, Linux via Docker container, Windows cross-build, both Docker image tars).
README, installer (`bin/openjevx.js`), `package.json`, Dockerfile, Taskfile, and ADR 0003 updated
to match. https://github.com/muthuishere/openjevx/releases/tag/v0.3.0

## Is 8-bit better than 4-bit?

No — ran an 8-bit weight-only build (`scripts/quantize_w8.py`, not shipped) for comparison:

| Model | Public test accuracy | Size | Time / 5-question case |
|---|---|---|---|
| v0.2.0 int8 (retired) | 65.1% | 598 MB | 0.15 s |
| **v0.3.0 4-bit (shipped)** | **77.0%** | 461 MB | 0.42 s |
| 8-bit weight-only (not shipped) | 76.9% | 598 MB | 0.55 s |
| fp32 | 77.4% | 1.7 GB | 0.40 s |

8-bit is not more accurate than 4-bit (same within noise), and it's larger and slower. 4-bit
stays the right call.

## Everyday-domain accuracy — still flat across quantization

| Model | My everyday set |
|---|---|
| v0.2.0 int8 (retired) | 45.8% |
| v0.3.0 4-bit (shipped) | 45.1–45.8% (two runs, different sample sizes) |
| 8-bit weight-only | 45.3% |
| fp32 | 46.8% |

Confirms report 1: quantization is not the everyday-domain gap. All four land within ~2 points
of each other, all near chance outside the four trained workflows.

## jevx CLI, run with real repo context

Ran `jevx is` / `ask` / `pick` / `filter` against two profiles (`openjevx` = shipped 4-bit,
`openjevx8` = 8-bit), piping this repo's actual `git log`, `git diff --stat`, and README as
context (no `## Jev` section configured, so just the repo's real state).

Finding: obvious facts (stock at 0 units, age 17, CI failed) mostly get the right *direction*,
but confidence is weak — `{"stock_units":0}` → "item is out of stock" scored 0.59–0.68, which
**jevx's own default thresholds (yes ≥0.8, no ≤0.2) classify as "unsure."** Even where the model
leans correctly, jevx can't act on the answer without loosening `-min`/`-no`. This is a
calibration problem distinct from raw accuracy, worth fixing in training (sharper, more
confident outputs on clear-cut cases) since jevx's thresholds are a sensible default, not a bug.

## fp32 model availability

Uploaded `openjevx-model-fp32.zip` (1.0 GB zipped, 1.7 GB unzipped) to the v0.2.0/v0.3.0 GitHub
releases with a `.sha256` checksum, for anyone who wants to run full precision instead of the
shipped quantized model (set `"model": "openjevx.onnx"` in `openjevx.json` after unzipping next
to the binary).

## Bottom line at this point

fp32 already clears 77%, so 80%+ on the public test looked reachable with better calibration and
more data. Everyday-domain accuracy needed a new fine-tune, not a quantization fix — that's the
target for the vast.ai training run, still pending owner approval before renting anything.
