## BGL regression (found after v0.5.2 was published)

On BGL (Blue Gene/L supercomputer log alerts, real loghub labels, 107 alert / 107 not), v0.5.2 misses alerts it
used to catch:

| Model | Alerts caught | Alerts missed |
|---|---|---|
| v0.5.0 | 58 | 49 |
| v0.5.2 run 1 | 30 | 77 |
| v0.5.2 run 2 | 32 | 75 |

Example: `RAS KERNEL FATAL Microloader Assertion` gets 0.02 from v0.5.2 and 0.88 from v0.5.0. Confidently wrong goes
from 21.0% to 35.0%, about 3 standard errors.

- **Not truncation.** BGL states are short (p90 342 chars). Swapping `max_len` (v0.5.2 at 1024, v0.5.0 at 512)
  changes neither model.
- **Not the BGL data.** Both shards have the same 9,414 BGL rows; FATAL lines are labelled true 4,678 vs false 1,030.
- **Most likely interference from the rule-reading drills.** Both runs that had them regress the same way. The drills
  are ~10% simple numeric/date yes/no rows, and "no" is the safe answer on many of them. A single-epoch reshuffle may
  add to it.

The release gate does not cover BGL: its logs gate is application/database/frontend logs, and it held at 7.8%. The
benchmarks ran after publishing, which reversed the order in docs/RELEASE_PROCESS.md (7 before 8). Fix candidates:
weight `bgl_logs_train` up, or add a BGL slice to the gate so this cannot ship unseen again.
